**ACP's dangerous failure is the agent that works against its author's test client and fails against everyone else's.** The handshake is small; what breaks is the part each real client checks differently: a capability the client never sent, a cancel that returns an error, a login that needs credentials before `initialize` can answer, a byte on stdout that is not a message. Three consequences drive the file: an omitted capability means *unsupported* · the prompt request's response is what ends a turn · the registry's auth check runs `initialize` with no credentials and reads only the result.

Read against ACP **v1** (`agentclientprotocol.com/protocol/v1/*`, 2026-11-07) and the registry's checker source (`agentclientprotocol/registry` `main`: `AUTHENTICATION.md`, `CONTRIBUTING.md`, `.github/workflows/client.py`, 2026-11-07). Nothing here was run against a live client or the registry CI. v2 is a separate, draft protocol (last section).

## The wire
- **stdio, one JSON-RPC message per line.** The client launches the agent; stdout carries only ACP messages (no embedded newlines), and logs go to stderr. A debug `print` on stdout breaks the framing. Both sides number their own requests, so one id can be live in both directions.
- **Order:** `initialize` → (auth) → `session/new` → `session/prompt` … with `session/update` notifications and `session/request_permission` / `fs/*` / `terminal/*` requests *from the agent* in between. Any request before `initialize` is `-32600`. The baseline an agent implements: `initialize`, `session/new`, `session/prompt`, `session/cancel` (a notification), and sending `session/update`. Everything else is a capability.

## `initialize`: capabilities gate behavior in both directions
- The client sends `protocolVersion: 1` (an integer) and `clientCapabilities`; the agent answers the same version when it supports it, otherwise its latest, and the client disconnects if it cannot speak that. **Omitted means unsupported**, so an agent calls `fs/read_text_file` / `fs/write_text_file` only when `fs.readTextFile` / `fs.writeTextFile` is `true`, and any `terminal/*` only when `terminal` is `true`; otherwise it reads its own disk and spawns its own processes. A receiver answers a method it did not advertise with `-32601`.
- The agent's answer carries `agentCapabilities` (`loadSession`, `promptCapabilities` for `image` / `audio` / `embeddedContext` — `text` and `resource_link` are always accepted — and `mcpCapabilities` for `http` / `sse`), `agentInfo`, and `authMethods`.

## Auth and the registry check
- **`authMethods` is part of the successful `initialize` result.** A method with no `type` is `agent`: the client calls `authenticate { methodId }` and the agent runs its own login. `type: "terminal"` makes the client re-run the agent binary with `args` appended and `env` (an **object** here) applied, then reconnect; it is allowed only when the client sent `clientCapabilities.auth.terminal`. A request that needs login fails with `-32000` (`auth_required`).
- **The registry's `--auth-check` is a pass/fail on that one result.** It starts the agent with an empty `HOME` (no saved credentials), sends `initialize` with `protocolVersion: 1` and `clientCapabilities` of `terminal: true`, `fs`, and `_meta: { "terminal-auth": true }` — and **not** `auth.terminal` — then passes only if the response is a result, not an error, whose `authMethods` holds at least one entry typed `agent` or `terminal` (`type` absent counts as `agent`; the `_meta` keys `terminal-auth` and `agent-auth` are read as a fallback). Four ways to fail it; the first and third are what `agentclientprotocol/registry#591` reports for an agent whose `initialize` returns an error telling the user to run `fx login` and whose success path returns `"authMethods": []`, and the second and fourth follow from the checker's source:
  - `initialize` answers differently with and without credentials. It answers the same either way; the missing login shows up as the `authMethods` entry and as `-32000` on `session/new`.
  - The only method is `terminal` and gated on `auth.terminal`. The checker never sends that flag, so an agent that follows the capability to the letter advertises nothing. Offer an `agent` method (the default) for the login flow, with the instruction a person needs (`Run … login`) in its `name` and `description`.
  - `"authMethods": []`.
  - The login hanging `initialize` on a browser or a prompt; the checker's handshake has a 120 s timeout and no terminal.

## `session/new`: the client hands the agent its MCP servers
- Params are `cwd` (absolute, and the session's root whatever the process's own working directory is) and `mcpServers`. The agent connects to each itself, so it is an MCP client (the `mcp` skill). The result is `{ sessionId }`; a later request naming an unknown id gets `-32002` with `data.sessionId`.
- **Two shapes carry `env`/headers, and neither is an object:** a stdio server is `{ name, command, args, env: [{ name, value }] }` (`command` an absolute path); an HTTP server is `{ type: "http", name, url, headers: [{ name, value }] }`. Stdio support is mandatory; `http` and `sse` are used only when `mcpCapabilities` advertised them (`sse` is deprecated upstream). Reading `env` as a map is the mistake, since the terminal auth method's `env` *is* one.

## The prompt turn
- `session/prompt { sessionId, prompt: ContentBlock[] }` is answered **once, when the turn ends**, with `{ stopReason }` — `end_turn`, `max_tokens`, `max_turn_requests`, `refusal` or `cancelled`. Everything before it is `session/update` notifications whose `update.sessionUpdate` is `agent_message_chunk`, `agent_thought_chunk`, `tool_call`, `tool_call_update`, `plan`, `usage_update`, and the others in the spec's table. An update sent after the response has no turn to belong to.
- **A tool call is announced, then updated:** `tool_call { toolCallId, title, kind, status: "pending" }` (`name`, the tool's programmatic name, is optional), then `tool_call_update { toolCallId, status }` through `in_progress` to `completed` or `failed`.
- **Permission is a request to the client:** `session/request_permission { sessionId, toolCall: { toolCallId }, options: [{ optionId, name, kind }] }` with `kind` one of `allow_once`, `allow_always`, `reject_once`, `reject_always`. The answer is `{ outcome: { outcome: "selected", optionId } }` or `{ outcome: { outcome: "cancelled" } }`. The agent owns `allow_always` — it stores the scope, which the option `name` states — performs only the operation the approved request described, asks again when the command or target changes, and treats an outcome it does not recognise as a refusal.
- **Cancel:** `session/cancel { sessionId }` has no response. The agent aborts its model requests and tool runs, may still send final updates, then answers the pending `session/prompt` with `stopReason: "cancelled"`. The abort surfaces in an HTTP client or a subprocess as an exception; **it must be caught and converted**, because an error response to the prompt is shown to the user as a failure and the client cannot confirm the cancel. A pending permission request resolves `cancelled` on the client's side; the agent reads that as the turn ending in `cancelled`.

## Client tools the agent may call
`fs/read_text_file { sessionId, path (absolute), line?, limit? }` returns the editor's buffer, unsaved changes included, which is the reason to prefer it over the disk when advertised. `terminal/create` returns a `terminalId`; `terminal/output`, `terminal/wait_for_exit` and `terminal/kill` use it, and `terminal/release` is required when the agent is done, `kill` included. A terminal can be embedded in a tool call's content to stream its output into the UI. A missing file or unknown terminal is `-32002`.

## Check it
`agentclientprotocol/acp-tck` drives an agent over stdio through initialization, sessions, prompt turns, cancellation, errors and transport hygiene. Its own page calls it experimental and not a conformance statement.

## v2 is a different protocol
v2 (`protocolVersion: 2`, `agentclientprotocol.com/protocol/v2/*`) is labelled draft in its own migration guide. It changes what this file relies on: `session/prompt` only acknowledges, and the turn ends with a `state_update` notification; `authenticate` becomes `auth/login`; the client `fs/*` and `terminal/*` methods and session modes are removed in favor of client-provided MCP servers; `session/load` becomes `session/resume`. A client may offer 2 to an agent that speaks only 1; the agent answers 1 and the client decides. Build v1, keep the version answer honest, and read the migration guide before any v2 work.
