A seat handed frame files and drawn widths works from those and needs no doop tools, so missing tools are no gap for it. Every other seat loads doop's own tool guide first: `get_guide({ topic: "doop-instructions" })`. Read against doop `aa5a395`; the `server/…` cites are that tree, except *A repo's component library*, read against `d458d27` (`server/componentTools.ts`).

## A `/c/<id>` link is read through the MCP tools
Canvases are private. With no signed-in user there is no role on a canvas, even through a view, comment or edit share link (`server/access.ts:33-35`), and every `/api` call without a session is a 401 (`server/index.ts:684-688`). A fetch of the `/c/<id>` link carries no session, so it cannot return frames; treat nothing that fetch returns as the design. A frame's `image_url` from `get_frame` is a separate public route (`server/index.ts:392`) and is fine to download. Take the id from the link and read it with the doop MCP tools this session already has: `get_canvas`, then `get_frame` per frame. With no doop tools, see *When doop isn't reachable*.

## Build from the frame, leave the canvas alone
- Before building a screen, read its frame's HTML (structure, copy, values) **and** its `get_frame_screenshot` (the render). Either alone misleads: the HTML hides what the browser did with it, the screenshot hides the values.
- The canvas stays unedited unless the task asks for a design change. Every HTML or size edit voids a frame's human sign-off (`server/mcp.ts:75`), and a design change belongs to the designer and PM.
- Transcribe into the repo's components and token file (`${CLAUDE_PLUGIN_ROOT}/references/ui-handoff.md`). A frame's hard-coded values are not the repo's tokens, and the `data-doop-*` attributes and the `<style data-doop-fonts>` block are doop's own bookkeeping (`server/guide.ts:118-122`, `server/guide.ts:228-229`), so they stay out of the code.
- Name each frame's `approvalStatus` in the return. The approval the design-spec gate wants is the PM's; doop's `ready_for_dev` is evidence of it, not a replacement.
- A frame at `needs_review` is held, not built: it was edited after a human signed it off, so building it builds a design nobody accepted. Build the other frames. The return lists each held frame with its status and asks the PM to confirm it. Only the PM's confirmation releases it, reaching the builder as a brief that names the frame and quotes that confirmation; the frame still reading `needs_review` then is expected. A canvas edit or a later `ready_for_dev` read by the builder does not release it. A frame at any other status, `draft` included, builds on the PM's approval in the brief (`${CLAUDE_PLUGIN_ROOT}/references/design-spec.md` → *What counts as a design spec*).

## A frame has one width
A frame is a fixed-size document, and its screenshot is rendered at the frame's own width and height (`server/screenshot.ts:389-394`); `get_frame_screenshot` takes no viewport (`server/mcp.ts:1788-1800`). Doop's suggested frame sizes are 1280×800 desktop and 390×844 mobile (`server/guide.ts:231`), not 1440 and 375.
- Read each frame's `width` and `height` from `get_frame`, and compare the built UI at the width the frame is drawn at: a 1440 frame against the build at 1440, a 1280 frame against the build at 1280. `${CLAUDE_PLUGIN_ROOT}/skills/visual-review/SKILL.md` sweeps 1440 and 375, so a frame drawn at any other width goes in its brief as an extra spec viewport.
- When no frame is drawn at 1440 or at 375, the mockups omit that width: report it as a gap, as `${CLAUDE_PLUGIN_ROOT}/references/design-spec.md` has it, and leave the frames at their drawn size (a resize voids sign-off). A screen the build spec marks desktop-only has no 375 frame by design, so that one is no gap.

## Handing frames to a seat that has no doop tools
`visual-reviewer` has no doop tools, so the dispatching thread reads the frames before the spawn and hands over each frame's screenshot as a file path, its drawn width, and that width as a spec viewport when it is not 1440 or 375. `get_frame_screenshot` returns inline base64 and writes no file, so download the frame's `image_url` from `get_frame` to a path outside the repo (`server/mcp.ts:268`, public route `server/index.ts:392`). The URL carries `scale=2`, so the file is twice the drawn width. A 429 is a render rate limit: retry after its `Retry-After` (`server/index.ts:417-420`). A frame that can't be handed over that way is a named gap in the brief.

## Designing on a canvas
Additions to the server's guide for the designer:
- A new canvas goes in the workspace the brief names, or else the one on a `**Doop workspace:** <id>` line in the repo's `AGENTS.md` or `CLAUDE.md`, or else the one the kru store maps to this repo, for a public repo that keeps internal ids out of its files. That map is the file `bash "${CLAUDE_PLUGIN_ROOT}/scripts/kru-store.sh" path patterns/doop-workspaces` prints, one `<owner>/<repo> <id>` or `<owner> <id>` line each, matched against the GitHub owner and repo of `git remote get-url origin`, the `<owner>/<repo>` line first; no file or no matching line means none names one. Pass that id as `workspace_id` to `create_canvas`, which itself refuses a workspace you aren't a member of or one without a Team plan (`server/mcp.ts:488-492`). When it refuses the chosen workspace, stop before drawing and end the run with that refusal for the PM, rather than drawing on a personal canvas the chosen workspace can't see. Read `git remote get-url origin` first: only a URL that carries the GitHub owner and repo matches a line, and a run whose origin has another form (a local path, a proxy host) matches none. A canvas created without a workspace is personal, and the workspace's members can't open it, so whenever this run's canvas is personal your final message says so.
- Doop serves `/a/` assets with a one-year immutable cache. To replace an image, upload a new asset and repoint the frames at it; an overwritten key keeps showing the old image.
- Size the frames 1440 and 375 wide (`${CLAUDE_PLUGIN_ROOT}/references/design-spec.md`), over the guide's defaults.
- Hand the PM the `/c/<id>` link as the mockups, with the build spec beside it (`${CLAUDE_PLUGIN_ROOT}/references/designer-handoff.md`). The build spec writes out the tokens, states and copy rules; the frame HTML does not stand in for it.
- A frame can't load the repo's CSS or self-hosted fonts, so it inlines the repo's real tokens and the real rules of the classes it uses, copied from the files rather than retyped, and its elements carry those real class names. Inline only what the frame uses; a block shared by every frame can live in `set_guidelines` (24,000 characters at most).
- Build each frame to render with JavaScript off, over the guide's line that inline `<script>` works (`server/guide.ts:225-226`): no `<script>`, `on*` handler attribute or `javascript:` URL, and prototype wiring stays in the `data-doop-*` attributes. An uploaded asset is a real image or font with no CSS or code inside it; that holds for an `.svg` too, which can carry both. A frame that loads code can pass `get_frame_screenshot` and still show blank in a reviewer's browser, so check it by reading its HTML and assets, not its screenshot.
- A font already in the canvas's `fonts` loads as it is, and a Google Fonts face through a `<link>`. A repo's self-hosted fonts go in as an `@font-face` sheet, weights and styles taken from the repo's own font CSS, in each frame's `<style>` or once in `set_guidelines`. Doop's font library reads weight and italic from the values stored in the file, not the style name (`server/fontFile.ts`, `weightOf` and `italicOf`), so an upload comes out with wrong weights and upright italics: never upload to it. Keep the sheet clear of doop's own `<style data-doop-fonts>` block (`server/guide.ts:227-229`). Check the screenshot shows the repo's faces, not fallbacks.
- A run that revises from comments follows `${CLAUDE_PLUGIN_ROOT}/references/designer-handoff.md` → *Revising from comments*.
- An icon's SVG path is copied from the repo's icon library for a glyph on its list, never drawn by hand.
- When the brief names a build account other than the one `get_profile` returns, your final message tells the PM to give that account access to the canvas before the build; a brief that names none, or the same account, needs no line. State another account's access only once you have read it. This run can't share it: the MCP has no sharing tool and link access is session-gated REST (`server/index.ts:1298-1304`). For the PM: a view-level link gives any signed-in account access (`server/access.ts:36-38`), and only the canvas owner can set a link or invite an account (`server/index.ts:1301`, `server/index.ts:1351`). A canvas this run created is owned by the account `get_profile` returns (`server/mcp.ts:496`); name that account in the message.

## A repo's component library
A repo opts in by naming a library canvas: a `**Doop library:** <canvas id>` line in its `AGENTS.md` or `CLAUDE.md`, checked first, else the line the kru store maps to it. That map is the file `bash "${CLAUDE_PLUGIN_ROOT}/scripts/kru-store.sh" path patterns/doop-libraries` prints, one `<owner>/<repo> <canvas id>` line each, matched against the GitHub owner and repo of `git remote get-url origin` by the origin rule above (`<owner>/<repo>` only: a library is per repo). No line in either means no library, and a repo with no library sees none of this: say so in one line where this step would start, then work as before. Ids stay out of public repo files.

The repo's design system (token file, components, ledger, any registry the repo uses) stays the source of truth; the library is a copy of it.

### Composing from the library
Everything here needs the run's canvas in the library's workspace, because publishing shares within a workspace (`server/componentTools.ts:692`).
- Call `list_components` on the run's canvas before the first frame. It returns the canvas's own `components` and, under `workspace_libraries`, what the workspace has published that this canvas does not use yet; anything listed is used through `<doop-use component="…">`, never redrawn, and writing the tag adds a library component linked to its library (`:157`). Props and slots are on the signature each entry carries. When the named library's components appear in neither list, the canvas is outside its workspace or nothing is published: say so and work as with no library.
- Pull a waiting update with `sync_component` on this canvas before drawing; with no `component` it pulls every waiting update (`:658`). A library component has no main on this canvas; it is changed only on the library canvas (`:639`), which is why this run keeps its additions in frames. It works on one canvas, and the run's own is the only one it touches. `update_library_everywhere` changes other people's canvases and is the human's call (`:730`): a run never calls it.
- The part map ties each element to its library component and that component's ledger row, or lists it as an addition with its reason. Additions are plain frame markup on the run's canvas (the frame rules above). A screen run never edits or publishes the library canvas.
- **The repo wins.** When a published component disagrees with the repo's current design system (a token value, a class rule, a missing state), draw that element from the repo as an addition with the reason "library out of date", and put a drift note in the final message naming each component and what differs.

### Library build mode
The designer skill names the opening line of the brief that selects it. The brief is the human's ask to publish, which `publish_library` waits for (`:692`).
1. Read the repo's design system as the designer skill's step 1 has it: token file, components, ledger, icon list, and any registry package the repo's UI uses.
2. With a library named, open that canvas and update it. With none, `create_canvas` in the repo's workspace (*Designing on a canvas*), named for the repo's library.
3. Build the components the app's screens actually use with `create_components`, at most 12 per call and primitives first, since a later entry may `<doop-use>` an earlier one (`:106`, `:314`); change one with `update_component`, `dry_run: true` first for one with instances (`:413`). Markup, classes and token values come from the repo's files, with the real rules inlined under the frame rules above: no scripts, real class names. Each component's `code` field is an object: `{ path, name }`, its source file and export name (`:59-65`). Tokens go in through the canvas tokens tools. The main is on a library canvas, so a change to one reaches another canvas only after the publish below and that canvas's own `sync_component` (`:111`).
4. Run `publish_library` with `dry_run: true`, then for real, and report `published`, `removed` and `used_by` (`:713-718`). A refusal (a workspace without the Team plan, or one that restricts publishing to its owner and admins) goes to the PM as it stands, and the run does not work around it (`:692`). Never `update_library_everywhere`.
5. Final message: the canvas link and id; the exact `<owner>/<repo> <canvas id>` line for `patterns/doop-libraries.md` for the PM to add, since the run commits nothing to the store; each component with its source file; the drift note, listing what the repo has that the library lacks and what differs.

## When doop isn't reachable
Doop takes an OAuth browser sign-in or an agent key in the client's MCP config (`server/mcp.ts:2076-2121`); a revoked key is a bare 401. When the doop tools are missing, the sign-in fails, or a read answers `no canvas … accessible to this account` (the connected account has no access to that canvas), report the gap to the PM, naming the MCP server to enable, the sign-in to finish, or the canvas to share with that account. Never ask for a key or token in chat, and never rebuild the screen from the URL or from memory. The slice that needs those frames waits as a named gap; the others proceed.
