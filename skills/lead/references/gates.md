# Review and verify — which gates a slice earns

Loaded by `lead` when the branch is live.

**A build return from a seat carrying Block O, with no `Return pass:` line, is unverified** — that line is the seat's own read-back of the finished slice (`${CLAUDE_PLUGIN_ROOT}/skills/roster/shared-blocks.md` → Block O), and its absence is the one defect every gate below is blind to, because a pass that never ran leaves no diff. Ask that seat for it — same-task reuse, inside the 2-loop cap — before the gates run. The brief never asks: the block rides in the seat prompt, and re-authoring it there is the restatement Step 3 refuses. The one seat Block O exempts (`test-writer`) never carries the line; its own bound — a green suite — is its verification.

**Done is judged on evidence, not the return's account of itself.** Before a build return is ready for the gates below, pair every behavior on the list you handed down (your grill, or `brief.md`'s `Done when`) with its proof — a test name, a command's output, a count, from the return or from your own scoped run. A behavior with no proof beside it is unbuilt until shown otherwise: send it back to that seat (same-task reuse, inside the 2-loop cap) before the gates below spend a review on it. Pairing is for accurate handoff — **evidence is not PM acceptance**; Step 5 marks each criterion with proof or **unproven** and the PM decides.

The review gates below are independent and read-only — batch the ones that only read source in one message (e.g. `code-reviewer` + `architecture-reviewer`), then merge their findings into one fix list for the builder. **In-build verification is tests, lint, and typecheck** (and other non-interactive CI scripts the repo runs) — not opening a preview, driving a browser, or walking a flow. The fix→re-review loop is sequential.

**A finding enters the fix list only when its trigger happens in normal use** — an ordinary user action, a provider's documented retry or redelivery, concurrency the real crons, retries and staff produce, data a UI or an import can create, an ordinary attacker. One that needs a convoluted trigger is dropped, one counted line in the report at most, never ranked or filed: our own keys or config failing once set (a key a *user* enters still gets validated and a clear error), a provider breaking its own docs, one human action racing itself within milliseconds, data no path can create, an attacker already holding our secrets or database, a vendor outage cited to justify new machinery, or several of these stacked. The same bar holds wherever a defect gets filed or fixed.

**Scale the batch to live-versus-latent.** The full batch is priced for a slice shipping a path something reaches today. A slice that is entirely latent — a fix behind a trigger this codebase doesn't have yet, a cleanup of a path nothing calls — takes one reviewer or none: an adversarial multi-agent pass over it returns findings about code that cannot run, and spends the review a live slice needed.

**Name a report path in every review brief.** A batch of six reviewers is the single largest thing your context ever ingests, and most of it is audit record you will never route off — passing rules, keyboard tables, path maps, screenshots, coverage matrices. Each seat's *What you return* contract splits the two, but it can only write the long half somewhere if **you** name where: hand it `report: ${TMPDIR:-/tmp}/kru-review/<project-slug>/<seat>-<slice-slug>.md` in the brief and you get back a capped fix list plus a pointer, instead of the report. A review brief naming none gets that path supplied by `hooks/check-handoff.sh`, the slice slug taken from the dispatch's description. This location is **deliberately ephemeral and outside the plan store**: a review is per-run, it has none of the four lifetimes `TRACKER.md` defines, and nothing durable may depend on it. What outlives the run is what you route (the fix list) and what you capture (`issues/<kebab-slug>.md`, Step 4.5) — never the report file. Never write it into the working repo.

**Hand down the intent, not only the diff.** A reviewer that gets files and a report path re-derives what the slice was *for* from the code that may have gotten it wrong — so it can catch *built wrong* and never *built the wrong thing*. Put the behavior list in the review brief: the one from your grill, or `brief.md`'s `Done when`, the same list the builder got (contract item 4, Step 3). It is the cheapest line in the brief and the only one that buys a whole class of finding.

- Structure: for a refactor or a new module boundary, spawn `architecture-reviewer` in **design mode** BEFORE the builder (settle the seam/interface), and in **review mode** after (gate boundary integrity). Skip for trivial or purely additive changes.
- Correctness: spawn `code-reviewer` — it reads for comment hygiene alongside the bugs. The built-in code-review skill inline is the fast path for a small diff — it runs as a background subagent, and with no level given reuses the last effort level the PM set (say code-review at high effort) — and reviews against CLAUDE.md, never `shared-blocks.md`, so **that fork keeps the comment pass yours**: read the diff's added comments against `skills/roster/shared-blocks.md` → Block I before you call the slice reviewed.
- Design spec: before UI builders run, the brief must carry the approved mockups and build spec (`${CLAUDE_PLUGIN_ROOT}/references/design-spec.md`). A **named gap** in the builder's return goes to the **PM** with the token name it would need — not to a seat.
- Tests: **first coverage is the builder's**, written test-first during the build (Step 3) — so for a behavior seat the work already arrives tested, and this gate reads the coverage rather than commissioning it. Spawn `test-writer` for what that doesn't reach: an **exempted** seat's output, coverage sweeps and fan-out across many files, repairing a red or flaky suite, and any repo whose testing conventions still have to be discovered from scratch. Either way, see the counts yourself, from a run scoped to the slice's changes — a builder's "tests pass" is a narrative until you have; a full suite runs only when the user asks, and a long run is dispatched, not run inline.
- Loop fixes back to the builder**s** — a merged fix list groups by seat exactly as the original change did (*Group the change's files by seat*, Step 3), so a list spanning two seats is two loops, not one brief handed to whichever seat the feature is named after. Findings arrive as `file:line`; contract item 2 (Step 3) converts each to its named anchor before dispatch. Max 2 loops per seat — a third grows one builder's context past its slice. Then the loop stops: surface only what someone using the product would notice, in their terms; the rest is one counted clause, and the full list stays in the report. A remainder the user wants fixed is a new slice for a fresh builder, never a third round.
