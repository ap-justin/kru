# Review and verify — which gates a slice earns

Loaded by `lead` when the branch is live.

**A build return from a seat carrying Block O, with no `Return pass:` line, is unverified** — that line is the seat's own read-back of the finished slice (`${CLAUDE_PLUGIN_ROOT}/skills/roster/shared-blocks.md` → Block O), and its absence is the one defect every gate below is blind to, because a pass that never ran leaves no diff. Ask that seat for it — same-task reuse, inside the 2-loop cap — before the gates run. The brief never asks: the block rides in the seat prompt, and re-authoring it there is the restatement Step 3 refuses. The three seats Block O exempts (`test-writer`, `brand-designer`, `ui-designer`) never carry the line; their own bound — a green suite, *Prove it at size*, the user's eye — is their verification.

**Done is judged on evidence, not the return's account of itself.** Before a build return counts as done, pair every behavior on the list you handed down (your grill, or `brief.md`'s `Done when`) with its proof — a test name, a command's output, a count, from the return or from your own scoped run. A behavior with no proof beside it is unbuilt until shown otherwise: send it back to that seat (same-task reuse, inside the 2-loop cap) before the gates below spend a review on it.

The review gates below are independent and read-only — batch the ones that only read source in one message (e.g. `code-reviewer` + `architecture-reviewer`), then merge their findings into one fix list for the builder. A seat that drives a browser or runs a suite fits the machine budget the session runs under (the user's `~/.claude/CLAUDE.md`): the two browser-driving reviewers run one at a time, never beside each other or a suite. The fix→re-review loop is sequential.

**A finding enters the fix list only when its trigger happens in normal use** — an ordinary user action, a provider's documented retry or redelivery, concurrency the real crons, retries and staff produce, data a UI or an import can create, an ordinary attacker. One that needs a convoluted trigger is dropped, one counted line in the report at most, never ranked or filed: our own keys or config failing once set (a key a *user* enters still gets validated and a clear error), a provider breaking its own docs, one human action racing itself within milliseconds, data no path can create, an attacker already holding our secrets or database, a vendor outage cited to justify new machinery, or several of these stacked. The same bar holds wherever a defect gets filed or fixed.

**Scale the batch to live-versus-latent.** The full batch is priced for a slice shipping a path something reaches today. A slice that is entirely latent — a fix behind a trigger this codebase doesn't have yet, a cleanup of a path nothing calls — takes one reviewer or none: an adversarial multi-agent pass over it returns findings about code that cannot run, and spends the review a live slice needed.

**Name a report path in every review brief.** A batch of six reviewers is the single largest thing your context ever ingests, and most of it is audit record you will never route off — passing rules, keyboard tables, path maps, screenshots, coverage matrices. Each seat's *What you return* contract splits the two, but it can only write the long half somewhere if **you** name where: hand it `report: ${TMPDIR:-/tmp}/kru-review/<project-slug>/<seat>-<slice-slug>.md` in the brief and you get back a capped fix list plus a pointer, instead of the report. A review brief naming none gets that path supplied by `hooks/check-handoff.sh`, the slice slug taken from the dispatch's description. This location is **deliberately ephemeral and outside the plan store**: a review is per-run, it has none of the four lifetimes `TRACKER.md` defines, and nothing durable may depend on it. What outlives the run is what you route (the fix list) and what you capture (`issues/<kebab-slug>.md`, Step 4.5) — never the report file. Never write it into the working repo.

**Hand down the intent, not only the diff.** A reviewer that gets files and a report path re-derives what the slice was *for* from the code that may have gotten it wrong — so it can catch *built wrong* and never *built the wrong thing*. Put the behavior list in the review brief: the one from your grill, or `brief.md`'s `Done when`, the same list the builder got (contract item 4, Step 3). It is the cheapest line in the brief and the only one that buys a whole class of finding.

- Structure: for a refactor or a new module boundary, spawn `architecture-reviewer` in **design mode** BEFORE the builder (settle the seam/interface), and in **review mode** after (gate boundary integrity). Skip for trivial or purely additive changes.
- Correctness: spawn `code-reviewer` — it reads for comment hygiene alongside the bugs. `/code-review` inline is the fast path for a small diff — it runs as a background subagent, and with no level given reuses the last one typed (say `/code-review high` to set it) — and covers correctness only, so **that fork keeps the comment pass yours**: read the diff's added comments against `skills/roster/shared-blocks.md` → Block I before you call the slice reviewed.
- Design work: **the gate is the user's eye, and there is no substitute for it** — conformance to a design is a judgment, not a measurement (`${CLAUDE_PLUGIN_ROOT}/references/ui-handoff.md`), so don't spend a browser sweep trying to replace it. Where the system is built from scratch this gate runs **twice, and the first run is the cheap one**: once in Claude Design, where the look is settled before a line of app code exists (Step 2, *UI from scratch*), then on the feature builds, where what's in question is only whether the build honors it. What you *do* owe the second run is the thing that makes it short — the builder invented nothing, because the token file is a closed set and the repo's own gate says so at every commit. A **named gap** in the builder's return is the one output you act on before the user looks: it goes to the **user** as the visible choice ("what colour for warnings?"), not to a seat — the token name it would need stays in the record and the builder's brief. The user reports back through you and you route each fix to the same builder (same-task reuse, inside the 2-loop cap), motion included — no separate motion gate.
- Screen passes: on UI work, spawn the two review-only seats after the source batch, one at a time — `accessibility-reviewer` (structural WCAG: keyboard, focus, target size, name/role/value, error identification — **contrast is the design's and ships as authored**) and `visual-reviewer` (the rendered states nobody opens + the cause behind a defect, only once a dev server is actually up — it never starts one; *up* is the port answering, so `curl` it before the batch, since a dev process left alive from an earlier seat can hold on to nothing, and a seat that finds no page falls back to a static read that verifies no rendered criterion). They are report-only and they **do not decide the design**: their findings merge into the same fix list as `code-reviewer`'s, and the user's eye above remains the gate. `references/screen-passes.md` carries how to brief them and the two rules that bound the batch. Skip both for non-UI changes.
- Tests: **first coverage is the builder's**, written test-first during the build (Step 3) — so for a behavior seat the work already arrives tested, and this gate reads the coverage rather than commissioning it. **A screen exemption you named is a slice you owe**: once that intent is settled, dispatch the covering run (the same-task builder, or `test-writer`) — an exemption that closes the loop unclaimed is how "relaxed" turns into "never." Spawn `test-writer` for what that doesn't reach: an **exempted** seat's output, coverage sweeps and fan-out across many files, repairing a red or flaky suite, and any repo whose testing conventions still have to be discovered from scratch. Either way, see the counts yourself, from a run scoped to the slice's changes — a builder's "tests pass" is a narrative until you have; a full suite runs only when the user asks, and a long run is dispatched, not run inline.
- UX (journey): when the change lands or reshapes a **multi-screen flow** (signup, checkout, onboarding), spawn `ux-auditor` on the flow by name. It walks the path statically — no browser — and returns findings ordered along the walk. Skip for single-screen or purely visual changes; those are the screen passes' scope — journey-scoped and screen-scoped are different lanes, and `ux-auditor` is the only one that walks between screens. Its `HEURISTIC` findings are questions, not defects — don't hand them to a builder as a fix list.
- Behavior: `/run` to confirm it actually works.
- Loop fixes back to the builder**s** — a merged fix list groups by seat exactly as the original change did (*Group the change's files by seat*, Step 3), so a list spanning two seats is two loops, not one brief handed to whichever seat the feature is named after. Findings arrive as `file:line`; contract item 2 (Step 3) converts each to its named anchor before dispatch. Max 2 loops per seat — a third grows one builder's context past its slice. Then the loop stops: surface only what someone using the product would notice, in their terms; the rest is one counted clause, and the full list stays in the report. A remainder the user wants fixed is a new slice for a fresh builder, never a third round.
