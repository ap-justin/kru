# Reconcile the plan, at the commit that lands a slice

Loaded by `lead` when the branch is live.

The plan must move with the code, not drift behind it. After the slice is verified and at the **same moment** as the commit that lands it, reconcile — this is **yours**, not a builder's or a subagent's, and it's automatic (write the files, report after; don't ask per-edit). The store lives outside the repo and doesn't ride in the PR, so reconciling as each slice lands is the only thing keeping `git log` and the plan telling the same story.

**The gate, stated once: the two captures have no precondition, the two reconciliations do.** `TODOS.md` and `issues/` are written whatever exists on disk — no store yet means you create the dir and the file, never that you skip the capture. Ticket status and the brief need a `plan/<effort>/` to reconcile against, so they're the only bullets an effort-less project skips.
- **Ticket status** — for every ticket whose acceptance boxes are all satisfied by what shipped, set `status: done`. Then recompute the **frontier**; it reaches the user only as the "next up: …" in the one-line report below, in product terms. Never mark done on unchecked acceptance — that's the one thing that makes the frontier lie.
- **Brief** — in `plan/<effort>/brief.md`: tick the `Landing plan` **commit** this slice just landed (and its parent PR box when that PR merges), tick the `Done when` boxes the slice satisfied, and correct `Blast radius` if the change reached further than the grill predicted. The PR's description is written from its `Change` + `Why now` + that PR's commit list.
- **Todo capture** — any want the **user pitches** mid-task, or one the **team discovers inside the effort in flight** (filed with that `plan: <slug>`), that's out of scope for the current slice: append a one-line entry to `TODOS.md` at the store root and **keep going** — never derail the task to build it. A freestanding want the team turns up — no plan in flight it belongs to — is the user's to file: name it in your report and leave `/kru:todo` to them. Capture is not only-at-commit: park it the moment it surfaces; this step is just the guaranteed catch-all sweep. It's a lossless, untriaged parking lot, deliberately outside `plan/` so it survives a brief rewrite — the next `brief` verb run reads it back to the user, who decides what gets pulled into scope. A line needs no evidence and no framework — just the line, carrying `value` and `effort` (`1`–`5`, `TRACKER.md`) answered from the context you already hold, written `~n` when the number is yours rather than the user's. The pair is what lets `/kru:todos` rank the file; it is not a priority call and it doesn't bind the user.
- **Todo closeout** — the other half, and it fires on the slices a `/kru:todos` run lands: **a slice that satisfies a parked want deletes its line** from `TODOS.md`, in that same reconciliation. `TODOS.md` is the open parking lot, never an archive — the commit is where the want is written down now. Outside a `todos` run you delete only a line the slice you just landed actually satisfies; the rest of the file is the user's.
- **Defect capture** — a known bug you're **not** fixing in this slice (surfaced by a reviewer, a test run, or the user) gets **its own file** at `issues/<kebab-slug>.md` in the store root: `severity` frontmatter, then call sites as `file:line`, observed behavior, root cause, repro, blast radius, fix options. A defect is something *wrong* (incorrect result, false info shown to a user, a condition it claims to handle and doesn't); something merely *wanted* stays a `TODOS.md` capture. Cite `file:line` always — the write-up sits outside the repo, so an unanchored reference is unfollowable.
- **Defect closeout** — the other half, and it fires on the slices the bullet above doesn't: **a slice that fixes a bug closes its file.** `ls issues/` and read the listing against what you just landed — every file whose defect this slice fixed is **deleted in that same change** (`issues/` is the open defect list, never an archive), and **the failing test that reproduced it lands in that same change too** (Step 3; a bug fix has no exemption). The two rules are one rule: deleting the file is what makes the test load-bearing, because once it's gone the test is the only place the defect is still written down. Completion criterion: **every file in `issues/` naming code this slice touched is deleted or explicitly kept** — "this slice fixed no known bug" is a claim you make *after* the listing, never instead of it.

Formats and lifetimes for all five are `TRACKER.md` → *Reconcile & capture*.

**Report the store in one line, in the user's vocabulary.** "Next up: …" — what's ready to be started, named as what it does for users, never as ticket ids — and the known bugs: how many stand open, what you wrote down, what this slice closed. A reconciliation nobody reports is indistinguishable from one that never ran — the store sits outside the repo, so this line is the *only* place a skipped sweep can surface before it has drifted for weeks.

**When the store outgrows its recurring read** — the files a run opens *every* time (`brief.md`, `TODOS.md`) cost more to read than the work they frame — compact it per **`${CLAUDE_PLUGIN_ROOT}/references/lossless-doc-compaction.md`**. Curate by that recurring read, never by total size. It's **relocation, never deletion**, so the store's total *grows* while the recurring read falls — report both numbers rather than a shrink that didn't happen. **Curating is not triaging**: moving decided/landed entries out is bookkeeping, deciding what's worth building stays the user's. It's blocking work — dispatch it, don't run it inline.
