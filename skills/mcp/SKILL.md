**An MCP client's dangerous failure is the one that works against the one server it was tried on.** The spec has two protocol eras on the wire, two homes for a failed tool call, and a remote server adds an OAuth dance whose every step has a way to succeed against the wrong party. Three consequences drive the file: the server decides which era it speaks and the client finds out by probing · a transport carries its era's rules · a `tools/call` can fail as a protocol error the model cannot fix or as a result the model should read.

Read against the MCP specification **2026-07-28** (current at the read; `modelcontextprotocol.io/specification/2026-07-28/`) and **2025-11-25**, the last `initialize`-era revision (`…/specification/2025-11-25/`), on 2026-11-07. Nothing here was run against a live server. A server is `extension-builder`'s (TypeScript, `skills/node`, the official SDK) or `python-developer`'s (`skills/python/reference/mcp-servers.md`); this skill stops at the client.

## Which MCP is the server speaking
- **Legacy (`2025-11-25` and earlier):** `initialize { protocolVersion, capabilities, clientInfo }` → result `{ protocolVersion, capabilities, serverInfo, instructions }` → the client sends `notifications/initialized`, and only then requests. The client sends its latest version; a server that does not support it **answers with a different version it does support**, and the client disconnects if it cannot speak that one. The spec's own error example is also a refusal: `-32602 "Unsupported protocol version"` with `data: { supported: […], requested }`. A client handles both shapes.
- **Modern (`2026-07-28`):** no handshake. Every request carries `_meta: { "io.modelcontextprotocol/protocolVersion": "2026-07-28", "…/clientInfo": {…}, "…/clientCapabilities": {…} }`, and on HTTP the `MCP-Protocol-Version` header with the same value (a mismatch is `400` / `-32020`). A server that lacks the version answers `-32022 UnsupportedProtocolVersion` with `data: { supported, requested }`; the client retries with a version in `supported`, and never falls back to `initialize` on this error, because it proves the server is modern. `server/discover` returns `supportedVersions`, `capabilities` and `serverInfo` on demand and every modern server implements it.
- **A client that has to reach both probes first, and caches the answer.** On stdio send `server/discover` with the preferred modern version: a result means modern; a recognized modern error (`-32022`) means modern, retry from its `supported`; **any other error, or silence for a reasonable timeout, means legacy**, so send `initialize`. The fallback never keys on one error code, because legacy servers answer an unknown method with `-32601`, `-32602`, or nothing. On HTTP try a modern request; a `400` whose body is a modern JSON-RPC error means modern, and any other `4xx` body means legacy. Cache the era per process (stdio) or per origin (HTTP) and re-probe when the cached guess starts failing.
- **The mismatch pairs fail without a fall-forward.** A legacy-only client against a modern server gets an `initialize` error or a `400`; the spec asks a modern-only server to name its supported versions in that error, so surface the message verbatim — it is the only diagnostic the user gets.
- **Modern results carry `resultType`.** `"complete"` is the answer; an absent field from a legacy server is `"complete"`; any other unrecognized value is invalid. `"input_required"` replaces server-to-client requests (sampling, elicitation, roots): the result holds `inputRequests` and a `requestState`, and the client **repeats the same call with a new JSON-RPC id**, adding `inputResponses` and echoing `requestState`.
- **`-32002` moved.** A resource not found is `-32602` in 2026-07-28. Codes `-32020…-32099` are the spec's (`-32020` HeaderMismatch, `-32021` MissingRequiredClientCapability, `-32022` Unsupported version); `-32000…-32019` are implementation-defined.

## Transports
- **stdio:** the client launches the server; one JSON-RPC message per line on stdin/stdout, nothing else on stdout; the server's stderr is logging, and a client does not read it as failure. A legacy client shuts a server down by closing its stdin, waiting, then `SIGTERM`, then `SIGKILL`. Credentials for a stdio server come from the environment the client launches it with, not from the HTTP OAuth flow.
- **Streamable HTTP, modern:** one endpoint, every message its own `POST` with `Accept: application/json, text/event-stream` (both) and the headers `MCP-Protocol-Version`, `Mcp-Method`, and `Mcp-Name` (for `tools/call`, `resources/read`, `prompts/get`). The answer is a JSON body or an SSE stream scoped to that request, and the client handles both. A notification gets `202`. There is no session id, no standalone `GET` stream, and no `Last-Event-ID` resume: a broken stream loses the request and the client re-issues it under a new id. Change notifications arrive on the response stream of a `subscriptions/listen` request. Closing the SSE stream is the cancel on HTTP; `notifications/cancelled` exists only on stdio.
- **Streamable HTTP, legacy:** the `initialize` response may carry `MCP-Session-Id`, which the client sends on every later request; a `404` on a request that carried one means the session ended, and the client starts over with a new `initialize`. Every request after `initialize` carries `MCP-Protocol-Version`. A client may open a `GET` SSE stream for server messages.
- **HTTP+SSE (`2024-11-05`)** is deprecated. To reach an old server, `POST` an `initialize` to the URL; on `400`, `404` or `405`, `GET` it expecting an SSE `endpoint` event, and use the old transport from then on.

## `tools/list` and `tools/call`
- **`tools/list { cursor? }`** returns `{ tools: [{ name, title?, description, inputSchema, outputSchema?, … }], nextCursor? }`; follow `nextCursor` until it is absent. Modern results add `ttlMs` and `cacheScope` (`public` or `private`), which say how long the list may be reused; the list may vary with the credentials presented and with nothing else, so a cache holds one list per credential.
- **`tools/call { name, arguments }`** takes `arguments` as an **object** matching `inputSchema`, and returns `{ content: [{ type: "text", text }, …], isError, structuredContent? }`; a tool with an `outputSchema` returns `structuredContent` conforming to it. Both `inputSchema` and `outputSchema` may use any JSON Schema 2020-12 keywords in 2026-07-28, including `$ref`.
- **Two failure homes.** A JSON-RPC `error` — unknown tool (`-32602`), a request that fails the schema, a server fault — is the protocol speaking, and a model rarely recovers from it. `isError: true` in a *result* is a tool execution failure (an API error, input validation such as a date in the wrong format, a business rule) with text meant for the model: pass it back so the model retries with other arguments. A client that turns `isError` into a thrown exception hides the correction loop; one that treats a JSON-RPC error as model-readable shows the model text it cannot act on.
- **The human stays in the loop.** The spec says a client should show a tool's inputs before the call, confirm sensitive operations, set a timeout on every call, and treat results as untrusted input to the model.
