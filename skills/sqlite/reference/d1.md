# D1 — SQLite the platform runs for you

Read `SKILL.md` first; this file stands where `embedded.md` does for a file the app opens. Verified against developers.cloudflare.com/d1 on 2026-09-13 — docs only, not reproduced on D1. The binding, `wrangler` config and local state are the `cloudflare` and `wrangler` skills'.

## Set for you, and not yours to set
- **Foreign keys are enforced on every query and migration**, and a query cannot turn them off: D1 wraps each query in an implicit transaction. The SQL statements page still lists `foreign_keys` as a compatible pragma — the foreign-keys page is the one that holds.
- **The embedded pragma block has no job.** `journal_mode`, `busy_timeout`, `synchronous` and `user_version` are absent from D1's supported list, and any pragma D1 accepts applies to the current transaction only.
- **`STRICT` is supported** and Cloudflare recommends it.

## The rebuild without step 1
The 12-step rebuild (`migrations.md`) opens with `PRAGMA foreign_keys=OFF`, which D1 won't run. In its place, the migration opens with `PRAGMA defer_foreign_keys = true`: violations are tolerated until the transaction ends, and step 10's `foreign_key_check` still runs before it does.

**Deferring does not stop `ON DELETE CASCADE`** (D1's own caveat), and SQLite's `DROP TABLE` runs an implicit `DELETE FROM` when foreign keys are on. Rebuilding a table that other tables reference with `ON DELETE CASCADE` therefore reaches step 6 with the cascade live — the same data loss the `drizzle` skill documents for the embedded rebuild. Both halves are documented; the combination is not reproduced on D1. Seed child rows and assert their count after the migration against local D1 before `--remote`.

## `batch()` is the transaction
`BEGIN`/`COMMIT` come out of the SQL — D1 already holds a transaction, and a nested one fails with `cannot start a transaction within a transaction`. `env.DB.batch([...])` runs its statements in order, and a failing statement rolls back the whole batch.

What a batch can't do is branch: every statement is fixed before the first runs, so a `[select, insert]` batch inserts on an empty select. A conditional write is the guarded write (`sql` → `queries.md`): one statement carrying its own guard, checked by rows changed.

## Migrations
- `wrangler d1 migrations create` / `apply`, recorded in the `d1_migrations` table under `migrations/` (both configurable: `migrations_table`, `migrations_dir`). No `user_version`.
- Apply `--local` and `--remote` separately; a migration applied to one is not applied to the other.
- `apply --remote` prompts and captures a backup first. It is still a one-way door for the app running against it — hand the command back, never run it.
- Whether each file runs in its own transaction is undocumented. One logical change per file keeps a failure's blast radius to that change.

## Backups
- **Time Travel** restores a database to any minute in the retention window: 30 days on Workers Paid, 7 on Free.
- `wrangler d1 export` **blocks other requests to the database while it runs**, and refuses a database with virtual tables (FTS5 included).
- No `VACUUM INTO`; D1's docs don't mention `VACUUM` at all.

## Limits that shape a schema
| Limit | Paid / Free | What it changes |
|---|---|---|
| bound parameters per query | 100 | a multi-row insert of 10 columns tops out at 10 rows — chunk the batch |
| row, string or BLOB | 2 MB | blobs go to R2; the row stores the key |
| SQL statement | 100 KB | a generated seed file splits |
| database size | 10 GB / 500 MB | a tenant-shaped dataset outgrowing it is a database per tenant |
| queries per Worker invocation | 1000 / 50 | a loop of single-row writes becomes one `batch()` |

## Read replication
Public beta, off until enabled — without it every query runs on the primary. Once replicas are on, a query outside a session can read a replica that is arbitrarily behind: read-your-writes is `env.DB.withSession("first-primary")`, carrying `getBookmark()` into the next request.
