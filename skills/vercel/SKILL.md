## Four environments, and the first deploy is always one of them
Three built-ins — **Development**, **Preview**, **Production** — map to git: a push/merge to the production branch deploys to Production, anything else (a branch push, a PR, `vercel` without `--prod`) deploys to Preview. ([`vercel.com/docs/deployments/environments`](https://vercel.com/docs/deployments/environments))

**The first deployment of a new project is always a production deployment** — even from a feature branch, even via dashboard import, even if it fails. A failed/errored/canceled first deploy still counts (only a deleted one doesn't, which resets the counter). The practical trap: *it builds with Production env vars*, not Preview's — a var scoped only to Preview isn't there yet.

**Custom Environments** (Pro: 1 included, 16 max per project; Enterprise: 12 included, 22 max) are a different thing from a preview branch, not a bigger version of one: a custom environment is named and persistent, with its own branch tracking, its own domain, and its own env-var scope that can start by importing from another environment and then diverge. A plain preview branch (all plans, including Hobby) gets a persistent domain too, but shares the one Preview env-var scope with every other branch unless a branch-specific var overrides it. Reach for a custom environment only when the workflow needs the isolation (`staging`, `QA`) — a preview branch covers "a named staging URL" on every plan without it.

## Env vars: where they're scoped, what never merges, and the two caps that aren't 64 KB
Scope is team-level (all projects) or project-level, and per-variable across Production / Preview / Development / named custom environments. **A branch-specific Preview var overrides the blanket Preview var of the same name** — no need to replicate every Preview var per branch, just the ones that differ. Changing a var is never retroactive: it only affects deployments built after the change.

Two size ceilings, not one: **64 KB total per deployment** (Node/Python/Ruby/Go functions), and a much smaller **5 KB per variable on the Edge runtime** — a var that's fine everywhere else throws there.

**`vercel env pull` merges into the existing file rather than replacing it** — local-only keys survive, logged as kept. Two exceptions that are *never* preserved from the local copy and always get overwritten: `VERCEL_OIDC_TOKEN`, and the Vercel-managed analytics ids (`VERCEL_ANALYTICS_ID`, `VERCEL_SPEED_INSIGHTS_ID`, `VERCEL_WEB_ANALYTICS_ID`). `vercel env run -- <cmd>` injects without writing to disk at all — reach for it over `pull` when the point is *not* leaving a secret in a `.env` file. `vercel build`/`vercel dev` read from the `.vercel/` cache `vercel pull` populates, not from `vercel env pull`'s output file — the two commands aren't interchangeable. ([`vercel.com/docs/cli/env`](https://vercel.com/docs/cli/env))

Config-vs-Secret storage defaults by target differ, and it matters for who can read a value back: Production and Preview default to **secret** (write-only after save), Development defaults to **config** (readable). A var with a public framework prefix (`NEXT_PUBLIC_…`) is always stored as config regardless of target.

**System env vars are off by default per project**, behind "Enable access to System Environment Variables" — leaving it off silently disables Skew Protection too, since that depends on `VERCEL_DEPLOYMENT_ID` being present. The one most worth knowing: **`VERCEL_ENV` only ever says `production`/`preview`/`development`; `VERCEL_TARGET_ENV` is the one that names a custom environment** — code branching on `VERCEL_ENV` alone can't tell a custom environment from an ordinary preview. `VERCEL_URL` can't be read on a deployment behind Standard Deployment Protection. `VERCEL_PROJECT_PRODUCTION_URL` is set on every deployment regardless of its own environment — the one to use for building an absolute URL (OG images, canonical links) that must point at prod even from a preview build. With **Fluid compute** (the default), the usual AWS Lambda internals (`AWS_LAMBDA_FUNCTION_NAME` and siblings) aren't accessible or loggable at all — code that introspects them for diagnostics silently gets nothing back.

## Deploys, previews, and the three ways to "promote" — only one rebuilds
Any push, a Vercel Drop, `vercel deploy`, a Deploy Hook, or the REST API triggers a build; a successful build is a deployment. Each deployment gets both a branch-specific preview URL (always the branch's latest) and a commit-specific one (pinned to that commit). ([`vercel.com/docs/deployments`](https://vercel.com/docs/deployments))

"Promote" names three different mechanisms, and conflating them is the trap:
- **Instant Rollback** — reassigns domains to a deployment that **already served production traffic**. No rebuild. Only eligible target: something previously aliased to production (most preview deployments never qualify).
- **Promote a preview to production** — a full **rebuild**, now against production config and production env vars. A preview deployment's own env vars don't carry over; expect different output if they differ from production's.
- **Promote a staged production build** — a deployment already built against the production branch/config but never domain-assigned (auto-assign was off). This one *is* instant, no rebuild, because it was already built correctly the first time.

**A deployment can only be promoted once** — "Promoted" is a one-way state; reusing an already-promoted deployment later means a rollback to it, not a second promote. Rolling back also **doesn't refresh env vars to current project settings** (it keeps whatever was baked in at its original build) and **doesn't restore custom aliases** unless those aliases were already on that exact deployment — and it **turns off auto-assignment of production domains going forward**, so the next ordinary push to the production branch does not retake the alias until someone runs `vercel promote` or hits "Undo Rollback." ([`vercel.com/docs/instant-rollback`](https://vercel.com/docs/instant-rollback))

Rolling Releases (Pro/Enterprise) shift traffic to a new deployment across stages instead of all at once — pair with Skew Protection, since mixed old/new clients hitting different deployments mid-rollout is exactly what it prevents. `vercel promote` on a deployment mid-rollout **jumps it straight to 100%** rather than advancing a stage — don't reach for the plain promote path during an active rolling release. ([`vercel.com/docs/rolling-releases`](https://vercel.com/docs/rolling-releases))

## Choosing a runtime: Edge is being phased out of the choice, not favored by it
**Vercel's own current guidance is to prefer Node.js over Edge** — "We recommend migrating from edge to Node.js for improved performance and reliability. Both runtimes run on Fluid compute with Active CPU pricing" — and in Next.js 16.3+, `runtime = 'edge'` on a route is no longer honored at all; it runs on Node regardless. Treat "pick Edge for low latency" as outdated advice, not a live tradeoff. ([`vercel.com/docs/functions/runtimes/edge`](https://vercel.com/docs/functions/runtimes/edge))

Edge's real constraint is API surface, not speed: no filesystem, no `require()` (ESM only), no `eval`/`new Function(string)`, Wasm only via static `import`, and exactly five Node-compatible modules (`async_hooks`, `events`, `buffer`, `assert`, `util`). It must start responding within 25s and may stream up to 300s total — a separate ceiling from the Node duration table below. Code size is capped by plan (gzipped): 1 MB Hobby, 2 MB Pro, 4 MB Enterprise.

Node is the default for anything under `/api` unless Edge is explicitly opted into, and gets the full Node API surface plus more RAM/CPU. The one architecture trap here: **Vercel builds one function per source file in `api/`** — a repo that mirrors "one file per endpoint" gets one cold-start-prone function per endpoint instead of letting Fluid compute reuse a warm instance across related routes. Group related routes into shared files.

**Fluid compute is an execution model both runtimes sit on, not a third runtime choice** — default for every project since 2025-04-23. Its two properties worth designing around: multiple concurrent invocations can share one warm instance (Node/Python currently; billed and isolated so one request's unhandled error doesn't kill the others sharing that instance — Vercel lets in-flight requests finish before recycling it), and billing counts **Active CPU time**, not wall-clock duration — time spent awaiting I/O (a DB query, an LLM call) doesn't bill as CPU time even though it extends `maxDuration`. A function that's mostly `await` is cheap on Fluid regardless of how long it runs. Setting precedence for `maxDuration`/`region`/`memory` when more than one place sets it: function code wins over `vercel.json`, which wins over the Dashboard, which wins over Fluid's own defaults. ([`vercel.com/docs/fluid-compute`](https://vercel.com/docs/fluid-compute))

## Functions: where to set a limit, and the one you can't set in vercel.json anymore
Framework-aware config lives in the file itself where the framework supports it — Next.js ≥13.5 (`export const maxDuration = N`), SvelteKit/Astro/Nuxt/Remix via their adapter config. Everything else — older Next.js, Go/Rust/Python/Ruby, or targeting many files by glob — uses `vercel.json`'s `functions` key, matched by glob with **order that matters** (first match governs). Python framework apps (FastAPI/Flask/Django) build into a **single** function at the resolved entrypoint — key the glob on that file, not on individual route files. ([`vercel.com/docs/functions/configuring-functions`](https://vercel.com/docs/functions/configuring-functions))

**Memory can no longer be set in `vercel.json` once Fluid compute is on** (the default for every project) — it's dashboard-only now (Functions settings), and a `memory` key left in `vercel.json` from an older setup is silently ignored with a build warning, not applied. `includeFiles`/`excludeFiles` in `vercel.json` are not honored by Next.js at all — use `outputFileTracingIncludes`/`outputFileTracingExcludes` in `next.config.js` instead. Per-function `region`/`functionFailoverRegions` **replace** the project-level default for that function rather than merging with it.

Current numeric limits (verify against `vercel.com/docs/functions/limitations` before relying on a number past a platform change): duration defaults to 300s on every plan, with Pro/Enterprise able to raise it to 800s GA or 1800s on an opt-in beta restricted to specific runtimes (`nodejs22.x`/`nodejs24.x`, recent Bun/Python) — Secure Compute and Static IPs don't support the beta tier at all. Memory defaults to 2 GB/1 vCPU on every plan (Hobby capped there; Pro/Enterprise can raise to 4 GB/2 vCPU) — **projects created before 2019-11-08 default differently** (1024 MB Hobby, 3008 MB Pro/Enterprise), a trap for anyone benchmarking an old project against current docs. Bundle size is 250 MB uncompressed (500 MB Python) standard, 5 GB on an opt-in "large functions" beta. **Request/response payload is a hard 4.5 MB ceiling that does not scale with plan** — unlike duration and memory, there's no higher tier to move to; a payload over it needs a different transport (direct upload, streaming), not a plan upgrade. Region count is plan-gated (1 Hobby, 5 Pro, all Enterprise) and an over-the-limit region list fails the deployment before the build even starts.

## Domains: the record type follows the domain shape, and two different flows attach one to an environment
Apex domains take an **A record** (the IP is on the project's own Domains settings page, never a value to hardcode); subdomains take a **CNAME**; a **wildcard domain requires Vercel's nameservers** (not just a record) because Vercel has to answer the ACME challenge to issue and renew the wildcard cert — a partial nameserver delegation of just `_acme-challenge` is the documented workaround when moving the whole apex isn't an option. A domain owned by another Vercel team needs a `TXT` record at `_vercel.<apex>` to verify — the same mechanism that lets a second team claim a subdomain without moving the apex's nameservers. ([`vercel.com/docs/domains/working-with-domains`](https://vercel.com/docs/domains/working-with-domains))

**Two different UI flows attach a domain to something other than production**, and picking the wrong one for the plan is the trap: assigning a domain to a **Git branch** under the plain Preview environment works on every plan including Hobby, from the domain's own Edit dropdown. Attaching a domain to a **Custom Environment** is Pro/Enterprise only, lives under a separate Environments tab, and always points at that environment's latest deployment rather than tracking a branch directly.

## `vercel.json` vs framework config: there's no one winner, it's per-setting
There's no blanket "vercel.json always wins" or "framework config always wins" rule — each overlapping setting resolves differently, and asserting a single precedence is itself the trap:
- `buildCommand`/`devCommand`/`installCommand`/`outputDirectory`/`framework` in `vercel.json` **override** both the Dashboard's Project Settings and `package.json`'s `build` script.
- `maxDuration` is framework-file-first where the framework supports it (see above); `vercel.json`'s `functions` key is the fallback for what can't set it in-file. If both somehow apply, function-code wins per the Fluid precedence table.
- `includeFiles`/`excludeFiles` **don't work in Next.js at all** — not a precedence loss, a capability gap; Next needs `next.config.js`'s tracing options instead.
- `memory` **can't be expressed in `vercel.json`** once Fluid compute is on (the default) — not an override question, the key is inert there.
- `rewrites`/`redirects`/`headers`/`cleanUrls`/`trailingSlash` are the documented preference over the legacy `routes` array (whose `handle`/`important`/`override` sub-properties are deprecated) for anything that isn't a true regex edge case. A `rewrites` `source` that names a real file never fires — the filesystem is checked first, so the fix is renaming the file, not tuning the rewrite. ([`vercel.com/docs/project-configuration/vercel-json`](https://vercel.com/docs/project-configuration/vercel-json))

## Not this skill's job
Deploying to Cloudflare's edge — Workers, Pages, D1, or anything under `developers.cloudflare.com` — is the `cloudflare` and `nextjs-on-cloudflare` skills' (`cloudflare-builder`'s). Web performance decisions on top of this platform (CWV, caching-for-speed, bundle/image/font tuning) are `vercel-perf-optimizer`'s, carried by the `vercel:*` first-party skills. App code behind these functions — Server Components, route handlers, Server Actions — is the framework builder's (`nextjs-builder`).
